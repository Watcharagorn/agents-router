# OpenCodex source study

Accessed 2026-10-14. Repository: github.com/lidge-jun/opencodex (MIT license per the README). Nothing was cloned, installed or run. Files were fetched through raw.githubusercontent.com and the GitHub contents API.

Evidence limits, read this first:

* The fetch tool returns summaries, not raw text. Every line range below is approximate (marked "~"), taken from a reader's estimate. Function and file names are reliable; exact lines need a local `grep -n`.
* The repository is very large (`src/` has about 50 top-level entries; single files such as `codex/account-store.ts` are 70 KB and `adapters/google.ts` is 90 KB). This is a targeted read, not an audit. Files read are named in each section. Not read: `src/codex/routing*`, `src/oauth/*`, `src/skills*` (if it exists), `src/claude/intercept/*`, `structure/INDEX.md`, the Cursor request builder.
* We do not copy code. This note describes behaviour only. Paths below are relative to the repository root.

## What OpenCodex is

A local proxy (Bun/TypeScript, default port 10100, dashboard included) that sits between a harness and a model provider. Codex talks the OpenAI Responses protocol to it, Claude Code talks the Anthropic Messages protocol, and OpenCodex translates both to whatever the target provider speaks (`src/adapters/*`, about 69 files, one per wire format such as `anthropic.ts`, `google.ts`, `openai-chat.ts`, `kiro.ts`, `cursor.ts`). It also manages OAuth tokens and pools of accounts. That token handling and the HTTP translation are what we will not copy.

One finding matters for us: it also contains a second, different route, `src/adapters/claude-cli/` plus `src/adapters/coding-agent/`, which spawns the official `claude` binary under the operator's own login instead of calling an API. This is the nearest thing in the project to our design (see question 1).

## 1. How tools are handled

**Short answer: tools stay in the harness.** OpenCodex has no MCP server registry, no tool store and no re-exposure of MCP servers. The harness (Codex or Claude Code) keeps its own MCP servers, runs its own tools, and sends tool definitions on every request. OpenCodex translates the definitions on the way out and the calls on the way back. The harness executes the tool and sends the result in the next request.

Evidence for "no MCP layer": `src/types/config.ts` (`OcxConfig`, ~487-890) has no MCP-related key. The only `mcpServers` / `mcpMaxTools` / `mcpMaxSchemaBytes` keys are on the Cursor provider config in `src/types/provider.ts` (~275-end), and their use was not found in `adapters/cursor.ts` (the logic is in `adapters/cursor/*`, not read). The README never mentions MCP.

**Tool definitions and names**

* Claude Code to Responses (`src/claude/inbound.ts`): `translateAnthropicRequest` calls `toolsToResponses` and `toolChoiceToResponses`. `tool_use` becomes a `function_call` item, `tool_result` a `function_call_output` item (`assistantMessageToItems`, `userMessageToItems`). A `tool_reference` block (Claude Code's deferred-tool loading) becomes a one-line text note, and a code comment says it must not create tools or widen authorization.
* Responses to Claude Code (`src/claude/outbound.ts`, `responsesSseToAnthropicSse` ~330-690 and `responsesJsonToAnthropicMessage` ~700-790): `function_call` becomes `tool_use` with the name passed through unchanged. Argument deltas are forwarded as `input_json_delta`. `stop_reason` is `tool_use` when any call was seen. The only name-based branch is WebSearch (`isClaudeWebSearchToolName` ~175-180): a Responses `web_search_call` is rewritten into Anthropic `server_tool_use` plus `web_search_tool_result` (`webSearchPairFromItem` ~212-245).
* Responses to Anthropic wire (`src/adapters/anthropic.ts`, `toolsToAnthropicFormat`, `buildToolNameTransforms`): namespaces are flattened into one name (`namespacedToolName`). In one mode (`escapeBuiltinToolNames`) every tool name gets a fixed `cx_` prefix on the way out and loses it on the way back; in OAuth mode a different Claude-specific prefix pair is applied. Tool-call ids are re-minted when blank or invalid, with a collision-safe allocator, and an unmatched call gets a synthetic error result.
* Kiro (`src/adapters/kiro-tools.ts`, `convertKiroToolContext` ~190-262): names are aliased to a safe form (no spaces, 64 characters max) and a `nameMap` is returned to restore them. Catalog caps are 48 tools and 96,000 bytes; when over budget a priority order decides what stays, and a system note lists up to 12 dropped tools. Tools are not emulated, only listed as omitted.

**Skills**

* `src/claude/inbound.ts` (`effectiveBlockedSkillNames`, `blockedSkillCallIds`, `maybeElideSkillText`, `skillElisionStub`): a configurable list `claudeCode.blockedSkills` (default `["claude-api"]`) causes Skill-tool results above 10,000 characters to be replaced by a stub. So OpenCodex edits what Claude Code's skills put into the conversation for non-Anthropic models, but it does not store or provide skills.
* `OcxSkillsConfig` (`src/types/config.ts` ~364-373) has a single `catalog_refresh` setting (`per_session` or `per_turn`), which controls whether the skills catalog is snapshotted across turns. Where it is used was not read.

**System prompts and instruction files**

* The Anthropic `system` field becomes Responses `instructions` (`anthropicSystemLayout`, `systemToInstructions` in `inbound.ts`). A `system` role inside messages becomes a `developer` item. With `stabilizePromptCache`, volatile parts (token-count footers) are removed so provider caches hit.
* CLAUDE.md and AGENTS.md are not read or rewritten anywhere that was found. Their content reaches OpenCodex only as ordinary system/user text from the harness. `AGENTS.md` in the repository is the project's own contributor guide.
* `config.injectionPrompt`, `injectionModel`, `injectionEffort` and `multiAgentGuidanceEnabled` exist as top-level keys (`OcxConfig`), apparently for a prompt OpenCodex adds for routed models; the code behind them was not read.
* Non-OpenAI providers get an added tool-catalog note (`src/adapters/tool-catalog-nudge.ts`, `buildNonOpenAIToolCatalogNudgeFromNames` ~92-130) saying which names are the complete top-level tool surface and that deferred helpers remain callable through a nested object. The file also special-cases an MCP server's own `exec_command` (arrives as `mcp__docker__exec_command`) so it is not mistaken for Codex's shell bridge.

**The CLI route: harness tools exposed to an official CLI (closest to our idea)**

* `src/adapters/claude-cli/adapter.ts` (`buildArgs` ~55-93, `buildChildEnv` ~33-53, `createClaudeCliAdapter` ~130-end) runs `claude` headless for a Codex request. The HTTP path is disabled. By default it passes flags that turn off the CLI's built-in tools, empty setting sources (no CLAUDE.md, skills, hooks, plugins), a strict MCP config with no file (no user or project MCP servers), no session persistence, and a per-turn system prompt file in a private temp directory that replaces the default preset. The prompt is written to a file so it is not visible in the process list.
* No API key is injected. The comments say OpenCodex "stores no Claude token, reads none, and injects none" (`claude-cli/profiles.ts` ~22-33). Inherited `ANTHROPIC_*` variables are stripped from the child environment to avoid a loop back into the proxy. A "not logged in" 401 is rewritten to an instruction to run `claude` and sign in (`withClaudeLoginHint` ~107-128).
* Each turn is stateless: the harness's conversation is replayed as one stream-json input message (`buildConversationInput` in `coding-agent/turn.ts` ~480-500, capped by a character limit scaled to the model context window).
* Optional tool bridge (`coding-agent/tool-catalog.ts` `buildCodingAgentToolCatalog` ~40-75, `coding-agent/mcp-server.ts` ~6-30, `coding-agent/turn.ts` ~285-330 and ~505-650): the harness's tool list is written to a private temp file and served by a tiny stdio MCP server whose `tools/call` never returns. The CLI is given exact allowed tool names in the form `mcp__<server>__<tool>` and an `--mcp-config` pointing at that stub. When the CLI emits a tool call, OpenCodex maps the name back (`emittedNameMap`), ends the turn with `stop_reason: tool_use`, kills the process tree, and returns the call to the harness, which executes it. Limits: 128 tools, 256 KB per tool, 2 MB catalog, 8 KB for the allowed-tools argument, names up to 512 bytes with no commas, spaces or control characters.
* Only three CLI families exist in the profile type (`claude`, `codebuddy`, `qoder`, `coding-agent/profile.ts` ~1-35). Codex and Antigravity are not CLI-wrapped here. Binary lookup tries `.cmd`, `.exe`, `.bat` on Windows (`whichFromPath` ~40-100) and caches only successes.
* Image input is rejected with 400 on this route.

## 2. Configuration storage

* **Home directory:** `$OPENCODEX_HOME`, default `~/.opencodex` (`src/config/paths.ts` ~21-29; `AGENTS_INSTALL.md`). Files: `config.json` (providers, models, accounts, routing), `admin-api-token`, `service.log`, `service-state.json`, optional `winsw/`. Service units go to launchd, a systemd user unit, or a Windows scheduled task named `opencodex-proxy`. Account credentials are held by the proxy (`src/codex/account-store.ts` and `src/oauth/*`, not read in detail). Docker keeps state in a named volume.
* **Format:** one JSON file. `OcxConfig` (`src/types/config.ts` ~487-890) groups keys by purpose: runtime and network; `providers` and `defaultProvider`; `customModels`, `disabledModels`, `defaultModelAliases`; `combos` and `routingProfiles`; `subagentModels` and fallbacks; `codexAccounts`, `codexPool`, `accountPoolStrategy`, `anthropicAccountPool`; sidecars (web search, vision, images); `claudeCode`; storage and spend limits.
* **Per-provider settings** (`OcxProviderConfig`, `src/types/provider.ts` ~275-end), about 100 fields in groups: identity (`adapter`, `alias`, `modelAliases`); endpoints (`baseUrl`, paths, proxy, TLS); auth (`authMode` of key, forward, oauth or local; `apiKeyPool`, `refreshPolicy`); model catalog (`models`, `selectedModels`, `modelPreset`, context windows, modalities, costs); reasoning-effort maps per model; per-model opt-out lists (`noVisionModels`, `noReasoningModels`, `noStructuredOutputModels`, and similar); tool-calling quirks (`codexToolMode`, `parallelToolCalls`, `unsupportedHostedTools`, `supportsResponsesCustomTools`); retries (`retryOn429`, `transientRetryOn5xx`, `requestPacing`); chat-wire compatibility flags; Google and Cursor specifics.
* **Model mapping:** `claudeCode.modelMap`, `tierModels`, `model`, `smallFastModel`, plus per-provider `modelAliases` and `reasoningEffortMap`. Alias scheme for Claude Code (`src/claude/alias.ts`): a routed model is exposed to Claude Code as `ocx-claude-<provider>--<model>`; ids containing `/` or `~` use an `ocx-claude2-` prefix with `~s` for `/` and `~t` for `~`; a hash-based id is the fallback; real Anthropic `claude-*` ids pass through unchanged; legacy `claude-ocx-` prefixes still decode (`aliasForRoute` ~89, `resolveAlias` ~139, `encodeModelId` ~54). A `[1m]` suffix marks 1M-token context and is added or removed according to the model's window (`src/claude/subagent-model.ts` `withSubagentContextMarker` ~44-60).
* **What it reads and writes in each harness's own config:**
  * Codex (`src/codex/inject.ts`, `injectCodexConfigImpl`): reads `config.toml`; writes a root `openai_base_url` pointing at the loopback proxy (or, for non-loopback binds, `model_provider` plus a `[model_providers.opencodex]` table), a model catalog path, and a separate profile file for `codex --profile opencodex`. It never overwrites a user-owned `openai_base_url` and does nothing if the user already has an external `model_provider`. Because Codex may rewrite the file and drop comment markers, ownership is also recorded in a journal with the injected values and the original content, and writes go through a lock, an atomic write, pre-image capture and rollback. Role models for Codex sub-agents are edited per file at `$CODEX_HOME/agents/<role>.toml`, only on explicit user action (`src/codex/agent-role-models.ts`, `setTomlRootString` ~52, `writeCodexAgentRoleModel` ~158), with the TOML validated before and after.
  * Claude Code: reads `settings.json` in the Claude config directory (only to learn the model chosen in `/model`) and writes custom agent files `<claudeConfigDir>/agents/ocx-<model>.md` (`src/claude/agents-inject.ts`, `buildClaudeAgentDefs` ~62-146, `renderAgentDef` ~156-187, `syncClaudeAgentDefs` ~199-251). Each file has YAML frontmatter (`name`, `description`, `model`, optional `effort`) and a body with a `generated-by: opencodex` comment marker and a routing directive that the proxy reads. Up to five roster entries plus an `ocx-self` file are written, stale owned files are pruned each sync, and files without the marker (or symlinks) are never touched. For the Claude Desktop and first-party CLI modes it also manages proxy settings inside Claude's `settings.json` (`src/claude/first-party-settings.ts`; the actual file I/O is in modules not read), with ownership tied to a CA certificate path.
  * Other integrations (`src/integrations/*`, about 30 files: registry, writer, merge, journal, ownership policy, serializers for Cline, Droid, Kilo and others) share one engine for planned, journaled, ownership-checked config edits.
* **Shared tool registry:** none. Skills, MCP servers and instruction files are not stored or merged by OpenCodex.

## 3. Several accounts or subscriptions per provider (described only)

* **Pools:** Codex has `codexAccounts` plus `codexPool`; Anthropic has `anthropicAccountPool` (`src/types/anthropic-account-pool.ts`), configured separately for the `anthropic` and `anthropic2` provider instances (neither inherits). API-key providers have `apiKeyPool` with `apiKeyPoolStrategy`.
* **Selection strategies** (`OcxAccountPoolRotationStrategy` ~10): `quota` (default; pick the least-used healthy account), `round-robin` (with `stickyLimit` 1-100 new-session binds per account), and `fill-first`. `quotaWindow` chooses which usage window drives scoring: `five-hour` (default), `weekly` or `max-utilization`. The README also lists a reset-first option. Accounts have a priority number (higher is used first; the desktop login has a synthetic key and can be made last resort) and an optional manual pin (`src/codex/account-priority.ts` ~16-80). Anthropic routes are ordered allowlists: a `name`, a `match` pattern on the model, and an ordered `accounts` list (`AnthropicModelRoute` ~14-19).
* **Switching and affinity:** `autoSwitchThreshold` (default 80 percent used) triggers choosing a new account for new sessions; 0 disables it. Existing conversations stay on the account that started them (cache affinity, on by default) unless quota, failover or an auth error forces a rebind (README).
* **Usability checks** (`src/codex/account-usability.ts`, `codexAccountUnusableReason` ~50-110): refused for missing model entitlement, hard lock, needs re-auth, missing credential, deleted, or validation pending. Cooldown and exhausted-window state are tracked elsewhere (`src/codex/routing`, not read).
* **Quota reading** (`src/quota/window-mapping.ts` ~33-112): usage windows of 5 hours, 7 days and 30 days, plus custom ones, each with percent used and reset time; an absent value is treated as unknown, not zero. Where the numbers come from (provider usage endpoints or response headers) was not confirmed.
* **Low-quota protection** (`src/codex/low-quota-protection.ts` ~24-200): per-account observer; when percent used reaches a configured threshold in the short or weekly window it can auto-pause the account and notify. An episode latches until the reading falls below the threshold or the window resets; there is no separate recovery band. A user's manual resume is respected for the rest of the episode.
* **Rate-limit handling per provider** (`RateLimitRetryPolicy`, `providers.<name>.retryOn429`, `types/provider.ts` ~60-100): opt-in wait-and-replay on HTTP 429 on the same target before any key failover; defaults 3 attempts, 5 s fixed wait, 60 s cap, honours `Retry-After`. Separate policies exist for 5xx and for reset replay.
* **Combos** (`src/combos/failover.ts`, `OcxComboConfig`): one virtual model id over ordered targets with strategies `failover`, `round-robin`, `random`, `least-used`, `reset-window` or an LLM-decided `jev`. Failure classification (`comboFailureDecision`): stop on client cancel, 499 and generic invalid-request; hop on 401, 402, 403, 404, 408, 425, 429, any 5xx and a list of quota, overload and context-overflow codes. Cooldown scope (`comboFailureCooldownScope`): none for request-shape failures, provider-wide for 401/402/403 and credential or billing codes, per target otherwise. Cooldown length (`coolComboTarget` ~231-283): server `Retry-After` first (up to 24 hours), then a parsed reset time, then the caller's value, then fallbacks of 10 minutes (exhausted window), 5 seconds (transient request-rate 429) or 60 seconds.
* **Health scoring** (`src/routing/health.ts`): a 14-day request history with 7-day half-life decay; score is 50 percent success rate, 15 percent complete-stream rate, 20 percent latency, 15 percent recovery (drops to zero after 5 consecutive failures). A live cooldown forces score 0. There is no circuit breaker or active probe in that file.

## 4. Cross-provider capability gaps

* **Capability evidence** (`src/routing/capability.ts`, `candidateCapabilityEvidence` ~149-239): per model it records context window, image support, tool support, reasoning efforts, service tier, local versus remote host, and encrypted Codex task support. Unknown stays unknown (not false); a routing profile's `unknownEvidence` policy (`allow` or `penalize`) decides eligibility. Tool support is positive only from catalog data, native models, tool-capable adapters or declared parallel tool calls. Web search is not tracked here. The evaluator that enforces requirements was not read.
* **Declared opt-outs:** the per-model lists in `OcxProviderConfig` (`noVisionModels`, `noReasoningModels`, `noTemperatureModels`, `noStructuredOutputModels`, `unsupportedHostedTools`, and similar) are operator-written facts that adapters use to drop or adapt request fields.
* **Schema translation:**
  * Google (`src/adapters/google-tool-schema.ts` ~5-660): allowlist-only rebuild of each schema (annotations like `title` and `default` never copied); inlines local `$ref`/`$defs` with a depth cap; collapses `anyOf` with one real branch plus null into `nullable`; merges enum-only branches; otherwise widens the union to an empty schema and records `union-widened` in a loss report; string enums only; string `const` becomes a one-value enum; arrays get default `items`; the root is forced to an object. Tool names are not changed.
  * Kiro (`kiro-tools.ts` ~21-143): strips a long list of keywords (`additionalProperties`, `pattern`, `format`, length limits, `$schema`), drops empty `required`, flattens root `oneOf`/`anyOf`/`allOf`, truncates descriptions (1,024 characters for most models).
  * Anthropic (`anthropic.ts`, `normalizeAnthropicInputSchema`): root forced to an object; root unions flattened, with same-named properties overwriting each other (a code comment admits it).
  * Responses (`responses-tool-schema.ts` ~31-228): removes a Responses-only `encrypted` marker, rewrites NUL escapes, strips regex patterns using Unicode property escapes. Other files exist for xAI (`xai-tool-schema.ts`).
* **Hosted tools:** a Responses web-search call becomes a native Anthropic server-tool pair on the way back to Claude Code. `webSearchSidecar` and `visionSidecar` config keys (also under `claudeCode`) run search or image reading through another model for providers that lack them. Not read in detail.
* **Request-field gaps** (`inbound.ts`): `top_k` dropped (no equivalent), thinking `budget_tokens` mapped to an effort tier, `stop_sequences` to `stop`, `output_config` to reasoning effort and text format, images to `input_image`.
* **Behavioural consistency:** mostly by per-provider flags, a loss report for schema changes, system-prompt additions that describe the real tool surface, and stream repair (tolerance for truncated JSON arguments, synthetic error results for unmatched calls, replay of unrepresentable calls as text). It does not try to make weaker models behave like stronger ones; failures are mapped to retryable or fatal errors and combos hop to another target.

## 5. What we can reuse as ideas, and what to avoid

**Reusable ideas for a CLI-based design**

1. **Official CLI as a model backend, with the harness keeping its tools.** OpenCodex already shows the shape: run the vendor CLI headless, give it no tokens, strip inherited variables that would redirect it, return tool calls to the caller. We differ in that the subagent runs a whole task itself with its own tools, but the launch recipe (tools off or on, strict MCP config, empty setting sources, system prompt by file path, no session persistence) maps directly onto the isolation modes in our design. The "not logged in" message rewrite is a good user-facing detail.
2. **Stub MCP server to advertise tools without executing them.** Useful if we ever need a worker to see the host's tool list while execution stays with the host. Note its limits (counts, byte caps, name rules); we would need our own caps.
3. **Config layout:** one home directory with an environment override (`OPENCODEX_HOME` pattern), one JSON file, provider entries with model lists, aliases and per-model capability declarations, ordered routes with account lists. Our equivalent would be accounts (config directories per login), runtimes, model aliases and a shared-tools manifest.
4. **Ownership discipline when editing a harness's config:** a visible marker in generated files, never touching unmarked or symlinked files, atomic writes, validating TOML before and after, a journal of what we injected (comment markers can be lost when a tool rewrites its own file), and never overwriting a user-owned key. Directly relevant to our links and launch flags for `config.toml`, Claude settings and agent files.
5. **Model-name mapping:** a reversible, escaped alias scheme (`<prefix><provider>--<model>` with a small escape table, hash fallback) so a vendor model id fits a harness's naming rules. Also the `[1m]` suffix treated as a marker that is stripped for identity comparison.
6. **Format conversion lessons for MCP config:** none of the three formats (Claude `mcpServers` JSON, Codex `config.toml`, Antigravity `mcp_config.json`) is translated by OpenCodex, so no MCP precedent exists to follow. What carries over is the pattern: allowlist-only rebuilding, a loss report listing what could not be expressed, name validation with a reverse map, and size budgets with a note about what was dropped. Applied to us: when a server cannot be expressed in a target format, say so in a report rather than silently dropping it.
7. **Limit detection and cooldown model:** classify failures into stop, hop-to-next, and cool-down-with-scope (none, provider-wide, per target); cooldown duration from `Retry-After`, then reset time, then fixed fallbacks with a cap; per-window usage (5 hours, 7 days) with percent used and reset time, absent meaning unknown; a threshold latch with no oscillation; a threshold that applies only to new sessions so running conversations stay put; priority numbers and a manual pin. We should read the vendor CLIs' own usage output or error text instead of API headers.
8. **Capability table with "unknown is not false".** Worth having for per-runtime features (tools, images, MCP, skills, hooks) so the delegate tool can warn or refuse.
9. **Stateless-turn trade-off, visible in OpenCodex:** replaying history into every CLI call is simple but costly and loses native resume. Our design resumes natively, which is better.

**Avoid**

* The proxy itself: token storage and refresh, OAuth for other vendors' subscriptions, forwarding one vendor's login into another's API (`oauth/*`, Kiro, Antigravity-OAuth adapters, `claude` OAuth tool-prefix mode), the account pool that uses subscription logins as API credentials, and the Claude Desktop man-in-the-middle setup (system proxy plus CA certificate in `src/claude/intercept/*` and `desktop-system-proxy.ts`). Those are the behaviours that break provider terms. Note that the project's own README says pooling is not endorsed for evading limits.
* Rewriting what the model sees (system-prompt elision, skill stubbing, injected catalog notes) to hide differences between models. It makes behaviour hard to predict.
* Combining cross-provider failover with silent model substitution. A subagent that quietly runs on a different vendor's model changes cost, safety and output quality; make every switch visible in the job record.
* Config size and surface: about 100 provider fields and hundreds of top-level keys come from hiding wire differences. Our CLI approach should not need most of them.
* Spawning without a process-tree kill on Windows. OpenCodex's own runner (`coding-agent/turn.ts` ~420-440, ~700-720) kills the tree with `taskkill /T /F`, then SIGTERM and SIGKILL with a grace period elsewhere; copy the idea, not the code.

## Takeaways for CLI Subagents

* OpenCodex keeps tools, MCP servers and instruction files in the harness. It stores no shared tool registry, so there is nothing to port; our shared pool is genuinely new ground.
* Its `claude-cli` adapter is the one piece that matches our approach: official binary, no injected token, `ANTHROPIC_*` stripped, tools and settings off by flag. Use that launch recipe for our isolated mode.
* Tool exposure to a CLI is done with a stub stdio MCP server plus exact `mcp__server__tool` allow names; calls are returned to the host. Consider it if a worker must see host tools.
* Edit harness configs the OpenCodex way: ownership markers, never overwrite user keys, validate TOML, atomic writes, and a journal (markers get lost).
* No precedent exists for translating MCP config between Claude JSON, Codex TOML and Antigravity JSON. Build it as an allowlist converter with a "could not express" report.
* Copy the shape of limit handling: stop/hop/cool classification, cooldown from `Retry-After` then reset time then a capped default, 5-hour and weekly windows, a threshold applied only to new sessions.
* Use a reversible model-alias scheme and a capability table where unknown is not false.
* Do not copy token pooling, OAuth relaying, the interception proxy or silent cross-vendor failover.
